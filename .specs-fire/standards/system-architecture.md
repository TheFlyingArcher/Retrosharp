# System Architecture

Full detail: `docs/architecture.md`. Summary:

## Overview

Retrosharp lets users explore historical baseball data from Retrosheet. It has an **import engine** (NServiceBus sagas that download, parse and load Retrosheet archives into PostgreSQL) and a **web application** (ASP.NET Core REST API + Angular SPA).

## Components

- **Retrosharp.UI.Web**: Angular 22 SPA; talks to the API over HTTP/JSON
- **Retrosharp.UI.Api**: REST API and send-only NServiceBus endpoint that starts imports
- **Retrosharp.Engine.Console**: NServiceBus endpoint hosting `PersonSaga`, `GameLogSaga`, `BulkGameEventImportSaga`, `GameEventSaga`
- **Retrosharp.Service / .Service.Interface**: business logic, statistics, import services, archive download
- **Retrosharp.Data**: EF Core context, repositories
- **Retrosharp**: domain contracts, messages, Retrosheet parsers, configuration, DI auto-registration
- **Retrosharp.Data.Migration**: one-shot migrations, seed data, NServiceBus schema
- **RabbitMQ**: queues `Retrosharp.Engine`, `.Errors`, `.Audit`
- **PostgreSQL 16**: application schema plus saga/outbox tables

## Data Flow

Reads: SPA → API → Service → Data → PostgreSQL.
Imports: API sends a command over RabbitMQ → Engine saga downloads from retrosheet.org → parses → bulk-inserts via Service/Data.

## Import Order

Seed data → People → Game logs (per season) → Play-by-play (per team file) → Standings

## Constraints

- Must run on ARM64 (Raspberry Pi self-hosting)
- Phase 1 is anonymous; auth/SSO is Phase 2
- Imports must be idempotent, enforced by database unique indexes

## Key Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Database | PostgreSQL | No ARM64 build for SQL Server |
| Long-running imports | NServiceBus sagas on RabbitMQ | Retries, error queue, progress tracking |
| Idempotency | DB unique indexes + skip-existing bulk insert | Safe reruns |
